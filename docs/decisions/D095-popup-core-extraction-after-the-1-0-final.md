## 2026-11-05 — D95: extract a shared popup core after the 1.0 final; retain conformance

- Context: `select-popup.ts` and `menu-panel.ts` duplicate popup positioning and dismissal logic. D86 correctly deferred the extraction before 1.0 and required a shared conformance suite so one host could not drift from the other. The owner task now explicitly approves extraction groundwork for the post-1.0 line.
- Decision: prepare `@rivinia/popup` as a headless package for the generic, behavior-equivalent popup logic. Keep the conformance suite and its mutation checks as the behavioral contract before and after each move. Owner approved adding Popup to the synchronized `rivinia-1.0` group; development version remains `0.0.0` and group alignment occurs only for a release. This branch is local groundwork only; it does not change existing Select/Menu public APIs, released versions, registry state, or the 1.0 release.
- D86 remains authoritative for the conformance requirements and the observed behaviors. This decision supersedes only its timing restriction (“no dedupe before 1.0”), not its test coverage, resize policy, or evidence.
- Keep component templates, CSS, row roles and states, controllers, keyboard ownership, and host-specific focus decisions in Select and Menu. Preserve every observed difference until an owner decision explicitly changes it.
- The core has no process-wide registry or mutable singleton. Position calculations are pure and receive direction as an explicit input; the core never reads host direction or computed styles. Any listener state is scoped to one popup binding and disposed with that host. The package is SSR-safe and imports no UI package.
- Select and Menu consume `@rivinia/popup` as a regular dependency, not a peer, so each consumer installation receives the core. The core's only peer is `@angular/core`; its package is headless, has `sideEffects: false`, and exposes one entry point unless a demonstrated need justifies another.
- A synchronized release that introduces the new runtime capability uses a minor bump: SemVer FAQ treats dependency-only updates as compatible and says the level depends on whether the change introduces functionality; this extraction does introduce a new runtime capability. A dependency metadata-only change without new behavior/capability may be a patch.
- Migration/rollback: adopt the exact popup version through regular package dependencies in Select/Menu; rollback by reverting those dependency/adapter changes and restoring the retained host implementation. The standalone package remains `0.0.0` until release alignment.
- Required gates: characterization tests and existing conformance/mutation contracts; popup/select/menu builds and unit suites; SSR safety; API snapshot unchanged for existing 1.0 packages; exact packed tarball inspection and clean consumer builds before release.
- Owner approval: the current task explicitly approves extraction and synchronized release-group membership. D89 was already assigned to the unrelated 2026-11-02 browser-floor/anchor-gate decision; this record uses D95 and preserves D89 unchanged.
