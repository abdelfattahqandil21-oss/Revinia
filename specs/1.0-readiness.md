# Rivinia 1.0 readiness: specs (v2)

Supersedes the first version. v2 folds in the agent's tree-verified corrections, the recorded decisions D85 to D88, the README plan (S9), and the reduced skill set.

Scope: `@rivinia/i18n` 0.8.0, `@rivinia/select` 0.7.1, `@rivinia/menu` 0.5.0, `@rivinia/theme` 0.1.0 (registry state 2026-10-31). The monorepo has **10 packages**; the first plan covered 4 (see S0).

## Ground rules for the agent

- One spec, one integration branch; small PRs; every PR links its spec and shows test evidence.
- The agent never runs `npm publish`, creates tags, changes dist-tags, force-pushes, or merges its own PRs.
- Verify each claim against the tree before changing code. If a claim is wrong, report it and adjust; do not implement the claim anyway.
- Public contract for 1.0 = exported TS API of every entry point + CSS custom property names (`--rv-*`) + documented ARIA roles and attributes.
- Browser support and ARIA rules come from primary sources (MDN, WAI-ARIA APG, WPT/caniuse), cited in the PR.
- Only the skills listed above exist. Do not assume others.

## S1. Peer ranges and release order

**Problem.** `@rivinia/i18n` peers on `@rivinia/select ^0.7.0`. Pre-1.0 caret means `>=0.7.0 <0.8.0`; any select 0.8.0 or 1.0.0 gives consumers of `@rivinia/i18n/select` an ERESOLVE until i18n is republished.

**Change.**
1. Publish order: theme, select, menu, then i18n. i18n 1.0 declares `@rivinia/select ^1.0.0`; the peer stays optional.
2. Keep the pack gate that only `rivinia-i18n-select.mjs` may mention `@rivinia/select/ui`.
3. Document the `@angular/*` peer policy in each README (`^22.0.0` or a wider range; decide and write it).
4. Add a cross-package compatibility table to the i18n README.
5. Apply the S0 audit result to every other package.

**Acceptance.** A clean Angular 22 consumer installs i18n + select from packed tarballs with zero peer warnings. Without select, i18n installs cleanly and ships no select code.

## S2. Select ARIA (D85)

**Problem.** Single rows are `menuitem` with no selected state. A text input sits inside `role="menu"`. Only axe has been run; no screen reader testing.

**Tasks.**
1. Capture the accessibility tree in Chromium for single, multi, searchable, disabled, RTL. Save snapshots.

5. Update README "Accessibility" and "Known verification gaps". Create `docs/testing/a11y-verification.md` with an empty matrix: NVDA+Firefox, NVDA+Chrome, VoiceOver+Safari, TalkBack+Chrome, JAWS (optional). Every cell starts as "not tested".

**Human gate.** The screen reader pass is done by a person. The agent leaves the matrix empty and never fills a cell it did not run.

**Acceptance.** Playwright and axe green for all variants. Verification doc lists real results only.

**Out of scope.** Full combobox/listbox rewrite (post-1.0).

## S3. Popup parity (D86)

**Tasks.**
1. Measure duplication between select and menu popup code with `jscpd`; report the real figure and the clone locations. Report only, not blocking.
2. One shared conformance suite parametrized over select popup and menu:
   - outside pointerdown closes without stealing focus

   - resize policy (S4)
   - top-layer fallback with `topLayerSupported = false`
   - add/removeEventListener balance after destroy

**Post-1.0 (separate spec).** Extract the shared popup core. Public API does not change.

**Acceptance.** Suite passes on both; breaking one component's behavior makes it fail.

## S4. Resize closes the panel

**Hypothesis (not confirmed).** Both components close on any `window` `resize`. On mobile, the on-screen keyboard (searchable select filter input) may fire resize and close the panel.

**Steps.**
1. **Human:** reproduce on a real iPhone (Safari) and Android (Chrome).
2. If it reproduces: ignore height-only resizes while an editable element inside the panel has focus (or compare `visualViewport`); still close on width change and orientation change.
3. If not: keep the behavior, document it, keep the test.

**Acceptance.** Playwright mobile viewport test: focus filter, shrink height, panel stays open; change width, panel closes. A note records the real-device result.

## S5. Theme (D87)

**Problem.** No dark mode or forced-colors anywhere; `--rv-accent` unused by components; theme is 0.1.0 with Unreleased SPEC-0.1.1.

**Split in two to avoid conflicts with S2.**
- **S5a, theme package (parallel with S2):**
  - dark values under `@media (prefers-color-scheme: dark)` guarded by `:root:not([data-rv-theme="light"])`, and `:root[data-rv-theme="dark"]`; keep `@layer rivinia-theme`
  - contrast script: WCAG AA (4.5:1 text, 3:1 non-text) for every token pair in both schemes
  - public token list documented in the theme README
  - fold in SPEC-0.1.1 per the S0 summary
- **S5b, component wiring (after S2 merges):**
  - `@media (forced-colors: active)` defaults using `Canvas`, `CanvasText`, `Highlight`, `GrayText`
  - `--rv-accent` read by the focus ring, selected/active indicator and the language toggle active state
  - with no theme imported, the look is identical to today (snapshot test)
  - check whether the i18n toggle animates; if so honor `prefers-reduced-motion`

**Acceptance.** One `:root` block or `@import '@rivinia/theme'` restyles all three libs including dark mode. Snapshots exist for light, dark, forced-colors, RTL.

## S9. README restructure

**Problem.** i18n 1416 lines, select 1351, menu 674. They open with a logo, a description and metadata bullets, with no quick hook. select 0.7.1's README says "Package version 0.6.0" and menu 0.5.0's says "0.4.0". Theming and migration notes are repeated inside each README.

**Readers.** One file served three audiences. The README serves the evaluator (10 seconds) and the installer (5 minutes). The customizer gets `docs/` pages.

**Template (same order and headings in every package; target 150 lines, hard cap 200).**
1. Name, badges, one-sentence pitch.
2. **Hook:** a working 8 to 12 line example using the **ready-made UI**, plus a screenshot or gif (or live demo link). The agent derives it from the existing quick start and proves it builds. The i18n exception: the core (translation) is the main path and the toggle/picker is step two of its quick start.
3. Three reasons to use it. "Headless first" becomes one bullet, not the headline.
4. Install.
5. Quick start, three steps.
6. **Two ways to use it** (table): ready-made UI (`.../ui`), headless controller (root entry), or both. One sentence: the two parts are independent; neither forces the other.
7. Compatibility table (Angular, Node, browsers) from S6 and S7.
8. "Go further" table with absolute GitHub links to the docs pages.

**Where the UI lives.**
- Basic: README hook and quick start (ready-made UI).
- Choice: the "two ways" table.
- Advanced: `docs/` only (customization, headless, recipes, theming).

**Destination map for select (agent assigns H3s the same way for other packages).**

| Current section | Goes to |
| --- | --- |
| Quick features | Hook + three reasons |
| Install, Imports, Quick start | README |
| API (inputs, outputs, controller) | `docs/api.md` |
| Forms (Signal, Reactive, template-driven, value types, form state) | `docs/forms.md` |
| The controller in the injector, Headless usage | `docs/headless.md` |
| Building a custom dropdown UI, Icons/avatars/custom rows, Paged data | `docs/recipes.md` |
| The override surface, Variants | `docs/customization.md` |
| Theming | One shared page owned by `@rivinia/theme`; select keeps only its own token table |
| Keyboard and focus, Accessibility | `docs/accessibility.md` |
| Migration notes | `CHANGELOG.md` |

**menu:** Ready-made menu and Inputs/outputs: quick start plus `docs/api.md`. Interaction and limitations: `docs/accessibility.md`. Headless usage: `docs/headless.md`. Override surface: `docs/customization.md`. Theming: shared page. Migration: CHANGELOG.

**i18n:** keep its three tiers as page names: Start here (README), Everyday use (`docs/guide.md` split by topic), Reference (`docs/reference.md` split by topic).

**Rules and gates.**
- No hand-written version numbers in prose; badges only.
- Same section order and heading names in all packages.
- Absolute GitHub links until how npm renders relative links is verified.
- CI fails if a README exceeds 200 lines, or contains a version string different from `package.json`.
- Link report in CI (non-blocking at first).

**Sequencing.** Template and gates now (with S1+S6). Content move after S2 and S8 step 1.

**Acceptance.** All READMEs on template within budget; every removed section exists in `docs/` with a link; gates green.
